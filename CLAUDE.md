# CLAUDE.md — правила работы над игрой

Этот файл читается первым в каждой сессии. Здесь — как работать. Что строить — в `docs/`.

## Документы проекта

| Файл | Что внутри |
|---|---|
| `docs/design.md` | Дизайн игры: цикл, системы, экономика, финал. Источник правды по механикам. |
| `docs/content.md` | Каталог контента: формы, шарики, камни, режимы, испытания, синергии. |
| `docs/ui.md` | Визуальный стиль и интерфейс. Референс: `docs/ui-reference.webp`. |

Если документы противоречат друг другу: `roadmap.md` решает порядок, `design.md` — механики, `ui.md` — внешний вид. Если не ясно — спроси, не угадывай.

## Про пользователя

- Автор идеи — Руслан. Общайся на русском, коротко и по делу, без воды и без лишнего смягчения.
- Он не программист. Объясняй результат простыми словами: что изменилось в игре и как это проверить (что открыть, куда нажать).
- В конце каждого этапа он играет и даёт обратную связь. Не начинай следующий этап без его «го».

## Стек (не менять без согласования)

- **TypeScript** (strict), **Vite**.
- **Canvas 2D** — арены и шарики.
- **Preact + @preact/signals** — интерфейс (дерево, панели, HUD).
- **Web Audio API** — весь звук синтезируется в коде, без аудиофайлов (позже можно добавить сэмплы).
- **Vitest** — тесты. **ESLint + Prettier** — стиль.
- Шрифты через `@fontsource` (см. `docs/ui.md`).
- Хостинг: **GitHub Pages**, деплой через GitHub Actions при пуше в `main`.

Новая зависимость — только если без неё код станет заметно хуже, и только после вопроса пользователю. Никаких игровых движков, физических библиотек, UI-китов.

## Архитектура

```
src/
  core/      rng, математика, форматирование чисел, шина событий. Ничего не знает об игре.
  sim/       детерминированная симуляция: мир, арены, физика, поведения форм/шариков, камни, триггеры.
  content/   ВЕСЬ контент как чистые данные: shapes, balls, gems, modes, tree, trials, synergies.
  game/      прогрессия, экономика, покупки, сохранения, оффлайн-доход, проверка условий.
  render/    отрисовка арен на canvas. Только читает состояние sim.
  audio/     синтез звука. Подписывается на события sim.
  ui/        компоненты Preact: дерево, панели, HUD, настройки.
  i18n/      ru.json, en.json.
tests/       зеркалит src/.
tools/       balance-sim, проверка контента и прочие скрипты для разработки.
```

### Жёсткие правила слоёв

1. **`sim/` не импортирует** ничего из `render/`, `ui/`, `audio/`, `game/`, не трогает DOM, `window`, `Date`, `Math.random`, `performance.now`. Только свой RNG с сидом и фиксированный шаг времени.
2. **Детерминизм:** фиксированный шаг `1/120 с`. Одинаковые сид + сборка + входы → одинаковый результат на любом устройстве. Порядок обхода коллекций стабилен (массивы, не `Set`/`Map` с непредсказуемым порядком в горячем коде). Есть тест: 10 000 тиков → хэш состояния совпадает с эталоном.
3. **`render/` и `audio/` только читают** состояние и события sim, никогда не меняют его.
4. **`content/` — только данные:** объекты, массивы, строки, числа. Без функций и классов. Поведение подключается по `id` через реестры в `sim/` (например, `effects/split.ts` регистрирует обработчик для `effect:split`). Это нужно для будущего переноса в Роблокс: данные переедут таблицами почти один в один.
5. **`game/` — единственное место** с экономикой: цены, доходы, покупки, разблокировки.
6. **`ui/` вызывает `game/`** через небольшой набор действий (`buyNode`, `socketGem`, `setMode` и т. п.), а не меняет состояние напрямую.

### Добавление контента = запись в данных

Цель архитектуры: новый камень, форма, шарик, узел дерева, испытание или синергия добавляются **одной записью в `content/`** плюс, если нужно новое поведение, **одним небольшим модулем-обработчиком** в `sim/`. Если для добавления контента приходится править много файлов — архитектура сломана, исправь её, прежде чем продолжать.

Узлы дерева не имеют ручных координат: раскладка строится автоматически по зависимостям (см. `docs/ui.md`).

## Правила чистого кода

- Файл — до ~300 строк, функция — до ~50. Больше — дели по смыслу.
- Один модуль — одна ответственность. Имена говорят, что делают, без сокращений.
- Никакого мёртвого кода, закомментированного кода, «на будущее» абстракций, неиспользуемых параметров.
- Не дублируй: если логика нужна в двух местах — вынеси. Но не обобщай то, что встречается один раз.
- Магические числа — в константы или в данные контента. Баланс — только в `content/` и `game/balance.ts`.
- Типы контента описаны в одном месте (`content/types.ts`), id — строковые литералы с префиксом (`shape:circle`, `gem:split`, `node:...`).
- Комментарии — только «почему», не «что».
- Все тексты для игрока — через `i18n`. Строки на русском в коде запрещены (кроме i18n-файлов).
- Без `any`, без `// @ts-ignore`. Ошибки не глотаются молча.

## Производительность

- 60 FPS на среднем телефоне при 300 шариках в одной арене и 1 500 суммарно.
- Пространственная сетка для столкновений, пулы объектов для шариков и частиц, без аллокаций в горячем цикле.
- Отрисовка не идёт, когда вкладка скрыта. Симуляция при скрытой вкладке останавливается, при возврате начисляется оффлайн-доход (см. `design.md`).
- Canvas учитывает `devicePixelRatio`.

## Тесты и проверки

Обязательно перед завершением любого этапа:

- `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` — всё зелёное.
- **Тест детерминизма** (см. выше).
- **Валидатор контента** (`tests/content.test.ts`): все id уникальны, все ссылки существуют, дерево без циклов, каждый узел достижим, у каждого камня есть теги и описан минус (`downside`), у всех текстов есть ключи в `ru.json` и `en.json`.
- Для механик — юнит-тесты на поведение (например: «Раскол создаёт клон, клон исчезает через 4 с»).
- С этапа 8 — `npm run balance` (headless-прогон прогрессии, см. `roadmap.md`).

Проверь игру в браузере сам (dev-сервер, скриншоты), прежде чем сказать, что готово. На телефонной ширине тоже.

## Как работать по этапам

1. Прочитай `docs/roadmap.md`, найди текущий этап.
2. Составь короткий план этапа и покажи пользователю (5–10 пунктов).
3. Делай маленькими шагами, коммить после каждого рабочего шага.
4. В конце этапа: проверки → обнови `docs/CHANGELOG.md` → задеплой → напиши пользователю:
   - что появилось в игре (по-человечески),
   - ссылку на игру,
   - 3–5 вещей, которые стоит проверить,
   - вопросы, если есть.
5. Жди обратную связь. Правки по ней — до перехода дальше.

Если по ходу появилась хорошая идея, которой нет в документах, — предложи её пользователю, не внедряй молча. Если идея из документов на практике оказалась скучной или ломает баланс — скажи об этом прямо и предложи замену.

## Git

- Ветка `main` всегда в рабочем состоянии и задеплоена.
- Сообщения коммитов на английском, в повелительном наклонении: `Add split effect`, `Fix ring collision at high speed`.
- Не коммить сгенерированное (`dist/`), секреты, большие бинарники.
